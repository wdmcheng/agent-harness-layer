[任务]
    结合当前上下文，理解用户接下来想自驱完成什么，按 Goal 模板写好一条 /goal 指令，交给用户复制发送。
    你只准备指令，不替用户触发。slash command 必须用户自己发。

[依赖检测]
    无前置文件。读当前对话和项目状态作为上下文。

[文件结构]
    goal-creator/
    └── SKILL.md  # 本文件，无 references / templates

[第一性原则]
    上下文感知：从当前环节、用户刚说的、项目状态里推断目标，不让用户从零写。
    目标必达：/goal 的核心是完成任务。执行策略写成目标导向、一条路不通就换方法，穷尽多种尝试都解不开才停，不一卡就停。
    完成条件可自证：完成标准和验证方式写成在输出里能自证的形式，因为 /goal 的 evaluator 只判已 surfaced 的内容。跑命令贴输出、列产出物、逐项打勾。
    字数硬限：/goal 有 4000 字符上限，超了发不出去。写到精准，每个字带信息，删套话、删多余的格式排版。完成条件之外的段不带信息就不写。
    边界要硬：有真实约束才写，比如别碰某模块、不直推 main。开发、修复、review 整改这类长轮次目标，要把项目主语言、注释/docstring/测试说明语言、OpenSpec artifact 语言、必要标识符保留英文等会漂移的规则压进约束里。目标涉及注释纪律或可维护性说明时，显式覆盖代码注释、docstring、测试说明、脚本说明、配置文件注释和配置示例说明，约束写成按共享纪律补足、重写或保留维护者需要的说明，并明确不改业务逻辑；避免“最小修正/最小补充”这类暗示降低说明充分性的措辞。别写"保持兼容性"这种放之四海的空话。
    不替下游规划：涉及 OpenSpec、发布、拆分、迁移等运行时决策时，只写完成标准和判断依据，要求执行者按当前环境规则现场拆；不要在 /goal 里预设名称、数量、边界或顺序。
    对外目标边界：/goal 只写用户可验收终态、必须在最终输出 surfaced 的验证证据和真实边界约束；可以写 code-reviewer Stage 1/2 PASS 这类最终输出能自证的验证结论；不得写 `.agents/.needs-review=clean`、本地 hook gate、临时 marker、缓存文件或类似内部执行状态，也不写下游 Skill 已规定的机械流程。
    不填形式：完成条件是唯一必填的核心，evaluator 全靠它。约束、验证、执行策略只在真带信息时写。简单目标就目标加完成条件两行。
    联网优先：涉及不确定的命令或接口先确认再写进模板。

[Goal 模板]
    核心是完成条件，必填且写到可自证。其余段按需，不带信息就删，整条压进 4000 字符。尖括号是占位。

    /goal 完成 <目标>。

    完成的标准：
    1. <可验证终态>
    2. <可验证终态>

    验证方式：
    - <跑什么命令、查什么产出物>

    约束：
    - <别碰什么、什么不可逆操作>

    执行策略：目标导向，一条路不通换方法，多种都试过才停；长任务记一句进度日志。

    执行策略是通用自驱行为，没有特殊打法就用上面这一行，别展开成清单占字数。简单目标只留目标加完成条件两行。

[工作流程]
    理解目标：从上下文确认用户要自驱什么，不清楚就问一句。
    OpenSpec 检查：项目存在 openspec/，且目标是全量开发、阶段开发、或从文档到代码的实现交付时，/goal 必须把 OpenSpec 边界写进完成标准或硬约束：先创建或选定 change，执行 `openspec validate <change> --type change --strict`，派 code-reviewer 做 OpenSpec artifact review 到 PASS；若 change 与 Product-Spec.md、DEV-PLAN.md、Design-Brief.md 或设计稿冲突，停下让用户决定；实现完成后只停在 ready-to-archive，不自动 archive。不要预设 change 名称，也不要替下游拆步骤。
    填模板：完成条件、验证、约束逐项填实，填不出的占位行删掉、套话删掉，整条压进 4000 字符。
    给用户：把写好的 /goal 整段放进代码块，附一句"复制这段发送即可启动 /goal"。
    提醒：涉及 commit、push、部署、删除等不可逆操作的，让用户发送前再扫一眼。

[初始化]
    读当前上下文，理解目标后按模板生成。
